# Physical Wi-Fi / CoreAudio investigation — 4 November 2026

**Follow-up accepted:** CoreAudio now uses 250 us polling by default. Windows
retains native notifications. The historical comparisons below predate that
promotion; see the [receive-service follow-up](ReceiveServiceInvestigation-2026-11-04.md)
for the implementation and more precise local receive timing.

The callback's native capture-wake notification is a reproducible contributor
to CoreAudio overloads on this Mac with the Focusrite. Separately, large incoming
audio gaps already exist at the kernel UDP timestamp, before the application
dequeues the packets. Removing callback notifications does not remove those
incoming gaps or the resulting playback underruns.

These results do not identify the commit that introduced the perceived
regression, establish that every Mac/device combination has the same cause,
or establish that all remaining delay is Wi-Fi rather than the sender or the
Mac's driver/network stack.

## Setup and measurement

The public universal Release executable was
`release/Jam2.app/Contents/MacOS/jam2`, built with Apple Clang. Each run used the
provided real Windows jam through the normal `network join` command, over the
Mac's `en0` Wi-Fi connection. The route selected was LAN/direct UDP between
the peers even though Jam2 Server handled discovery. Windows stayed on its
existing build. Session audio was Fast, PCM16 mono, **44100 Hz / 64 frames per
packet**. Both Mac devices used actual **32-frame CoreAudio callbacks**,
approximately **725.6 us per callback**, except the explicitly labelled
64-frame Focusrite comparison.

Devices were Scarlett 2i2 USB
(`AppleUSBAudioEngine:Focusrite:Scarlett 2i2 USB:Y82G60M961344A:1,2`) and Aggregate
Device (`~:AMS2_Aggregate:0`, built-in microphone/speakers). Real input/output
was active; software fake audio was used only in the separate native CTests.
Local monitoring was off and send/receive levels were 0.1. No Wi-Fi, AWDL,
power, or system scheduling settings were changed for the comparisons.

Each case has a command, PID, UTC window, device UID, executable SHA-256,
runtime log and native stats CSV under
[`artifacts/remote-jam-20261104`](../artifacts/remote-jam-20261104).
[`summary.json`](../artifacts/remote-jam-20261104/summary.json) and
[`summary.csv`](../artifacts/remote-jam-20261104/summary.csv) are generated by
[`summarize.py`](../artifacts/remote-jam-20261104/summarize.py).
The complete comparison table is
[`measurements.md`](../artifacts/remote-jam-20261104/measurements.md).
The Python files supervise/analyze real runs; they are not product-validation
tests or implementations of the audio/network path.

Steady-state deltas start at the first periodic row at/after 10 seconds and
end at the last row at least 3 seconds before the final row. Thus startup and
the intentional end-of-stream audio detachment/linger do not inflate those
rates. Whole-run maxima are explicitly whole-run measurements. CoreAudio
listener counters are checked against per-PID unified-log skipped cycles.
Compiling and CTest loads were kept outside physical measurement windows.

CPU measurements, where available, use child process user+system CPU time
divided by elapsed wall time: **100% means one logical core**. They include
the real app, its normal two-second telemetry, audio, and network work.

## Native callback notification

The normal call chain is CoreAudio IOProc → `push_network_capture_callback`
→ `RealtimeWakeSignal::signal` → `signalNative`. On macOS/POSIX the last step
calls `write()` on a pre-created, nonblocking pipe so the network worker's
socket wait returns promptly. Nonblocking pipe capacity does not guarantee a
bounded duration through the BSD/kernel notification path. Apple's archived
[CoreAudio overload guidance](https://developer.apple.com/library/archive/qa/qa1467/_index.html)
explicitly warns about BSD calls taking kernel locks from an IOProc.

Three explicit diagnostic modes make the comparison inspectable:

| CLI setting | Callback behavior | Network behavior |
|---|---|---|
| `--capture-wake on` | Existing atomic notification plus native wake | Existing immediate notification; default retained |
| `--capture-wake off` | Capture ring publication; no wake attachment | Checks capture after the bounded receive wait |
| `--capture-wake poll` | Same wake atomics, coalescing and ready timestamps; suppress native notification | Checks capture after the bounded receive wait; dispatch delay remains measurable |

`--capture-poll-us 50..1000` sets the receive-wait ceiling while waiting for
capture in poll/off modes; default 1000 retains the existing ceiling. This is
not a scheduler deadline: other work and OS descheduling can exceed it.
Capture sample timestamps, packet pacing, authentication and recovery remain
the production path in all three modes.

The original Focusrite run produced **64 overloads in 180 seconds**, with
**2862 us** maximum callback elapsed time. Using one subsequent executable,
off/on/off runs of 90 seconds produced **0 / 28 / 0 overloads** and maximum
callback times of **15 / 2910 / 15 us**. A further native-notification control
with kernel diagnostics produced **24 overloads / 2922 us**, whereas atomic-only
polling produced **0 / 15 us**. The polling run still published tens of
thousands of atomic wake notifications, so removing all shared wake state is
not necessary for this improvement.

Elapsed callback time includes descheduling. This ablation identifies the
native notification and its scheduling interactions as a contributor; it does
not measure the exact kernel lock or exclusive CPU time inside `write()`.
The pipe-notification implementation is present in commit `fd371dd8` from
23 August 2026. That is evidence of an existing weak path, not proof of the
historical regression's introducing commit.

The Aggregate baseline at 44.1 kHz produced one startup overload and **zero
steady-state overloads**. Its OS log attributes that startup event to a safety
violation/page faults. Last night's repeated Aggregate/48 kHz overloads remain
distinct from this cleaner 44.1 kHz Aggregate baseline; today's result does
not invalidate that recording.
The final Aggregate/32-frame/250 us polling run had **zero overloads over
60 seconds**, **8 us** maximum callback time and **162.5 us** mean dispatch
delay. All 12 physical case counters matched the per-PID OS skipped-cycle
counts exactly. The cases contain 19 minutes of requested streaming in total.

### Polling cost and the larger-callback comparison

The two 32-frame Focusrite runs with `--capture-wake poll --capture-poll-us 250`
recorded **zero overloads over 90 + 60 seconds**, each with **13 us** maximum
callback elapsed time. Average callback-ready-to-dispatch delay was
**163.2 / 169.8 us**, compared with **34.9 us** in the final 60-second native
control, which had **15 overloads**. Default 1000 us polling averaged about
**620 us**. Polling controls a bounded socket wait, not a hard scheduling limit.

Process CPU was **10.88 / 10.90% of one core** for the two 250 us polling runs
and **10.72%** for the final native control. These are short observations on a
varying live network, not a precise CPU benchmark. The measured additional
dispatch delay is approximately **0.13 ms**; true outgoing wire spacing and
remote Windows playout still require their own measurement.

With 64-frame callbacks and native mode, one 60-second Focusrite run produced
**zero overloads / 12 us** maximum callback time, but **zero native wake signals**.
It therefore did not exercise the suspect call and cannot establish that a
larger IO budget made that call safe. It also reported **200 input / 90 output
driver latency frames**, versus 168/58 at 32 frames: a 64-frame increase in the
combined reported driver latency, about **1.45 ms**.

Capture queue depth is an additional latency candidate. Across 24 steady
periodic samples, the 64-frame run held **64–128 frames**, median **128**; the
32-frame native control had median **64**, and both 250 us polling runs had
median **32**. These are stats-phase queue samples, not measurements of each
packet's capture age. The existing pacer spaces an exactly-one-packet backlog;
with equal callback and packet sizes, each callback can replenish that backlog
before it empties. This is a plausible retained-latency mechanism requiring
a dedicated packet-age/spacing experiment before changing anti-burst behavior.
Increasing the callback size is not an equivalent substitute for the isolated
notification fix in these results.

## Incoming packets and local service delay

`--receive-timestamps on` enables optional macOS `SO_TIMESTAMP_MONOTONIC`
ancillary timestamps on the real multiplex sockets. This is off by default;
unsupported platforms report an error when explicitly enabled. It adds no
wire fields. Apple's
[XNU `ip_savecontrol`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/ip_input.c)
records `mach_absolute_time()` for this option. The SDK identifies the ancillary
payload as `uint64_t`; conversion uses the actual Mach timebase.

Structured multiplex stats expose per-link kernel audio-gap counts/sum/max,
counts over 10/50 ms, socket residence counts/sum/max, counts over 1/4 ms, and
the residence time **paired with the largest kernel gap**. They are in the
runtime log's `UDP multiplex stats` JSON. Existing CSV columns keep their
positions. This timing never substitutes for the application-delivery time
used by drift, buffering or recovery.

In the 90-second native-notification timing control, the largest kernel gap was
**291.150 ms**, followed by only **0.683 ms** socket residence for that packet.
Across 61,483 measured audio packets, average residence was **0.297 ms**, maximum
**4.846 ms**, with 107 samples above 4 ms. Those smaller local delays deserve
attention but cannot account for that 291 ms interarrival gap. Classification
and control ingress had no queue drops; no WAV/asset traffic was present.

Kernel timestamps are taken after earlier NIC/driver/network processing.
Gaps before this point could involve the Windows sender, access point/radio,
or the Mac's lower network stack. They do not, by themselves, prove which one.
Header packet capture was unavailable because `/dev/bpf` requires administrator
access and passwordless sudo is unavailable; no password or system-setting
change was requested.

The 1 ms cooperative receive-service guard does trigger under this physical
burst pressure. It checks between packets, so its configured value is not a
hard cap on wall time during OS preemption. Its benefit should not be inferred
from zero-valued send-catchup/interval columns: those existing counters are
not populated by the current active send loop. Packet rate only establishes
throughput, not packet-spacing quality.

## Latency and quality interpretation

Fixing the callback notification did **not** eliminate playback underruns:
steady-state requested frames without ring data ranged roughly **7.5–11.4%**
across the Focusrite cases. The lower polling-run counts also coincided with
smaller upstream kernel gaps; they do not establish that polling fixes network
delivery. Those counts can overlap mixer shortage/recovery counts;
they must not be summed. Sequence loss was usually zero despite these late
deliveries. Packet preservation is different from meeting a live playout
deadline when gaps greatly exceed the Fast profile's buffering allowance.

The CSV's `estimated_one_way_ms` is RTT/2 plus configured jitter buffering,
average local playback depth and a callback allowance. It is not an electrical
end-to-end latency measurement, and excludes the driver input/output latency
fields. At 32 frames/44.1 kHz, the Aggregate reported **2487 input / 652 output
frames**, versus Focusrite **168 / 58 frames**. Their sums are about **71.18 ms**
and **5.12 ms**, respectively, as reported by the drivers. Do not add these
blindly to another estimator with overlapping allowances or interpret them as
a newly measured acoustic/ADC-to-DAC round trip.

No drift-correction, startup-buffer, packet-format, session-profile or
production-default change was selected from this investigation. The new
controls and diagnostics make candidate behavior reviewable; the user decides
whether to promote a polling policy into normal GUI sessions.

## What is worth taking forward

- **Strong candidate:** 32-frame CoreAudio with atomic-only capture wake
  publication and an explicit 250 us worker poll ceiling. It removes the
  reproduced overload path while retaining a low measured dispatch delay.
  Normal GUI and Windows notification defaults are unchanged for review.
- **Useful diagnostics:** keep optional kernel-gap/socket-residence metrics
  separate from actual delivery timing. They distinguish large upstream gaps
  from the app's smaller service delays without needing root packet capture.
- **Next latency investigation:** measure capture age at packet send and the
  equal-callback/packet-size retained backlog. Periodic queue snapshots identify
  a candidate but do not justify changing anti-burst behavior yet.
- **Not demonstrated fixes:** a larger callback as a cure for the notification
  call, more recovery buffering as a cure for HAL overruns, or replacement of
  delivery timestamps by kernel arrival in the recovery controller. The last
  approach already failed the earlier deterministic delayed-service tests.
- **Still unresolved:** what produces the gaps before the UDP kernel timestamp.
  A Windows-side sender trace/stats comparison would separate sender spacing
  from delivery through the access point and Mac network stack. Today's data
  cannot assign that remainder solely to the network or clear either platform.

## Native validation

All **nine focused CTests passed** in optimized Release; the full suite was
not run. The final log is
[`ctest-final.log`](../artifacts/remote-jam-20261104/ctest-final.log).

- `jam2_four_capture_wake_runtime`: eight real application/controller/transport
  conditions, exactly four participants per condition, Direct and Server,
  native/poll/off notifications and 1000/250 us polling, 32-frame synthetic
  callbacks. Requires sustained bidirectional packets, no capture overflow,
  configured notification behavior and real kernel timing on macOS.
- `jam2_udp_receive_timing_units`: real loopback socket ancillary timestamps,
  intentional 10 ms application queue residence, monotonic gaps, moves,
  disabling, truncated datagrams, unsupported-platform error, and atomic-only
  wake coalescing/rearm without a native wait notification.
- `jam2_cli_boundary_units`: defaults, mode parsing and invalid values,
  numeric polling limits, timestamp option contracts and existing CSV schema.
- `jam2_core_boundary_units`, `jam2_receive_budget_units` and
  `jam2_udp_multiplex_units`: existing core/receive/transport boundaries.
- `jam2_udp_four_peer_rotation_integration`: existing exactly-four-peer
  impaired delivery/ordering workflow.
- `jam2_udp_four_ingress_boundary` and
  `jam2_udp_four_ingress_mixed_budget`: classifier/shared-budget ordering under
  control prefixes and interleaved audio in an authenticated four-peer mesh.

The earlier unrelated core-input assertion failures were not changed or
hidden; their controlled baseline audit remains in the
[network ingress investigation](NetworkIngressInvestigation-2026-11-04.md).
